9. Sicherungen und Wiederanlauf

Eine Sicherung (Backup) ist eine Kopie aller Daten, aus der man das System wiederherstellen kann. Der Wiederanlauf ist der Weg zurück zu einem laufenden System nach einem Ausfall.

Warum es wichtig ist

Server fallen aus, Festplatten gehen kaputt, Menschen löschen versehentlich Daten, und Angreifer verschlüsseln Systeme gegen Lösegeld (Ransomware). Ohne Sicherung ist dann alles weg. Und eine Sicherung, die man nie probeweise zurückgespielt hat, ist oft unbrauchbar, genau dann, wenn man sie braucht.

Was man konkret tut

Drei Ebenen von Sicherungen.

  1. Täglich ein verschlüsseltes Komplettarchiv auf dem Server selbst. Schnell zur Hand, schützt aber nicht vor dem Verlust des Servers.
  2. Eine Kopie auf einen zweiten Server an einem anderen Standort, 30 Tage aufbewahrt. Schützt vor dem Ausfall eines ganzen Rechenzentrums.
  3. Monatlich eine Offline-Kopie auf eine verschlüsselte SSD. Offline heißt: nicht mit dem Netz verbunden. Ein Angreifer, der die Server übernimmt, kommt an diese Kopie nicht heran.

Asymmetrisch verschlüsseln. Bei asymmetrischer Verschlüsselung gibt es zwei Schlüssel: einen öffentlichen zum Verschlüsseln und einen privaten zum Entschlüsseln. Der Server kennt nur den öffentlichen Schlüssel. Er kann also Sicherungen erstellen, aber nicht lesen. Der private Schlüssel liegt getrennt und offline. Ein Werkzeug dafür ist zum Beispiel age.

Wöchentliche automatische Wiederherstellungsprobe mit Alarm. Ein Skript spielt die letzte Sicherung in eine Testumgebung zurück und prüft, ob die Daten vollständig sind. Schlägt das fehl, gibt es einen Alarm. Eine Sicherung ohne Probe zählt nicht.

Ziele festlegen.

  • RPO (Recovery Point Objective): Wie viele Daten darf man höchstens verlieren? Bei ASEIO höchstens 24 Stunden.
  • RTO (Recovery Time Objective): Wie schnell muss das System wieder laufen? Bei ASEIO in höchstens 8 Stunden.

Diese Ziele sind der Maßstab für alles andere: Wie oft gesichert wird, wo die Kopien liegen und wie der Wiederanlauf geübt wird.

Kein Deploy mit Datenbank-Änderung ohne geprüfte Sicherung. Ändert ein Deploy den Aufbau der Datenbank, muss vorher eine aktuelle, geprüfte Sicherung da sein. Geht die Änderung schief, ist das der Rückweg.

So macht es ASEIO

ASEIO sichert auf drei Ebenen: täglich ein verschlüsseltes Komplettarchiv auf dem Server, eine Kopie auf einen Sicherungsserver an einem zweiten deutschen Standort mit 30 Tagen Aufbewahrung und monatlich eine Offline-Kopie auf eine verschlüsselte SSD. Die Verschlüsselung ist asymmetrisch, der Server kann die eigenen Sicherungen nicht entschlüsseln. Jede Woche läuft automatisch eine Wiederherstellungsprobe, die bei Fehlern Alarm schlägt. Die Ziele sind höchstens 24 Stunden Datenverlust (RPO) und höchstens 8 Stunden bis zum Wiederanlauf (RTO). Ein Deploy mit Datenbank-Änderung startet nur mit geprüfter Sicherung.

Woran man erkennt, dass es klappt

  • Das Ergebnis der letzten Wiederherstellungsprobe ist grün und nicht älter als eine Woche.
  • Man weiß, wo der private Schlüssel liegt, und er liegt nicht auf dem Server.
  • Die Offline-Kopie des letzten Monats existiert und ist beschriftet.
  • Ein Wiederanlauf wurde schon einmal komplett geübt und dauerte weniger als das RTO.

Typische Fehler

  • Sicherungen nur auf demselben Server wie die Daten.
  • Der Server kann seine eigenen Sicherungen entschlüsseln, also auch ein Angreifer auf dem Server.
  • Nie probeweise wiederherstellen.
  • Den Alarm der Probe in ein Postfach schicken, das niemand liest.
  • Keine festen Ziele, deshalb weiß im Ernstfall niemand, was „schnell genug“ ist.
  • Datenbank-Migration live einspielen, ohne frische Sicherung.
