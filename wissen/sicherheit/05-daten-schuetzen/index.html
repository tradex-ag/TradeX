5. Daten schützen

Warum es wichtig ist

Eine SaaS-App hält oft die wertvollsten Daten ihrer Kunden: Zugänge zu Marktplätzen und Warenwirtschaften, Preise, Bestellungen, Kundenadressen. Gelangen diese Daten nach außen, kann ein Angreifer im Namen des Kunden handeln. Daten schützen heißt: verschlüsselt speichern, verschlüsselt übertragen und an keiner Stelle mehr zeigen als nötig.

Was man konkret tut

  • Zugangsdaten der Kunden verschlüsselt speichern, mit AES-256-GCM. AES-256-GCM ist ein bewährtes Verschlüsselungsverfahren. Es verschlüsselt und erkennt zugleich, ob jemand die Daten verändert hat. Der Schlüssel dafür liegt getrennt von der Datenbank. Wer nur die Datenbank stiehlt, kann die Zugänge nicht lesen.
  • In der Oberfläche nur maskiert zeigen. Ein gespeicherter Schlüssel erscheint nur teilweise, etwa als ••••••••1234. Der Nutzer kann ihn ändern, aber nicht anzeigen. So hilft auch ein übernommenes Konto oder ein Blick über die Schulter nicht weiter.
  • TLS 1.2 oder 1.3 überall, HSTS mit langer Laufzeit. TLS verschlüsselt die Verbindung zwischen Browser und Server (das Schloss in der Adresszeile). Ältere Versionen gelten als unsicher. HSTS (HTTP Strict Transport Security) sagt dem Browser: „Verbinde dich mit dieser Seite nur noch verschlüsselt.“ Mit langer Laufzeit merkt sich der Browser das dauerhaft.
  • Fehlermeldungen ohne Interna. Nutzer sehen nur eine allgemeine Meldung mit einem Fehlercode. Das Server-Log hat denselben Code mit allen Details. So kann der Support den Fehler finden, ohne dass der Browser Datenbanknamen, Pfade oder Code-Ausschnitte sieht. Rohfehler (die originale technische Fehlermeldung) gehen nie an den Browser.
  • Geheime Header und persönliche Links aus den Zugriffslogs heraushalten. Ein Zugriffslog hält jede Anfrage an den Server fest. Darin dürfen keine Webhook-Signaturen, internen Geheimnisse oder persönlichen Download-Links stehen. Ein Webhook ist eine Nachricht, die ein anderer Dienst automatisch an die App schickt, abgesichert mit einer Signatur. Wer das Log liest, soll damit nichts anfangen können.
  • Preise, Margen und Einkaufspreise nur auf dem Server. Alles, was im Browser-Code oder in einer API-Antwort steht, kann jeder Nutzer lesen. Interne Kalkulationen gehören deshalb nur auf den Server. Der Server rechnet und schickt nur das Ergebnis, das der Nutzer sehen darf.
  • Analyse-Skripte nur auf öffentlichen Seiten und nur mit Einwilligung. Analyse-Skripte messen, wie Besucher eine Seite nutzen. Im eingeloggten Bereich könnten sie Kundendaten mitlesen, deshalb haben sie dort nichts verloren.

So macht es ASEIO

ASEIO speichert die Zugänge der Händler zu Marktplätzen und Warenwirtschaften mit AES-256-GCM. In der Oberfläche erscheinen sie nur maskiert und lassen sich nur ersetzen. Unerwartete Fehler beantwortet die App mit einer allgemeinen Meldung und einem Fehlercode, den das Server-Log ebenfalls enthält. Preisaufschläge und Einkaufspreise bleiben auf dem Server, Kunden sehen nur das Ergebnis. Analyse-Skripte laufen nur auf den öffentlichen Seiten nach Einwilligung.

Woran man erkennt, dass es klappt

  • In der Datenbank stehen Zugangsdaten nur als unlesbarer Text.
  • Kein Weg in der Oberfläche zeigt einen gespeicherten Schlüssel im Klartext.
  • Ein absichtlich ausgelöster Fehler zeigt im Browser nur Meldung und Code.
  • Eine Suche im gebauten Browser-Code nach Margen oder Einkaufspreisen findet nichts.
  • Ein Test der Seite mit einem TLS-Prüfwerkzeug zeigt nur TLS 1.2 und 1.3 und HSTS.

Typische Fehler

  • Zugangsdaten im Klartext in der Datenbank, „weil die Datenbank ja geschützt ist“.
  • Ein „Anzeigen“-Knopf für gespeicherte Schlüssel.
  • error.message direkt an den Browser zurückgeben.
  • Ganze Anfragen samt Headern ins Log schreiben.
  • Preisberechnung im Browser, weil es bequemer ist.
  • Analyse- oder Chat-Skripte global für alle Seiten einbinden.
