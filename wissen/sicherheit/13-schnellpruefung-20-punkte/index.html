13. Die 20-Punkte-Schnellprüfung

Diese Liste passt auf jede Web-App. Sie sammelt die Fehler, die in der Praxis am häufigsten vorkommen, und ASEIO hat sie selbst durchlaufen. Für jeden Punkt steht da, worauf man achtet, und wo das Thema ausführlich erklärt ist. Wer die Liste mit einem KI-Assistenten durchgehen will, findet einen fertigen Prompt auf der Seite Prompts für dein Projekt.

Die Liste

  1. Auth nur in der Middleware. Prüft jede API-Route die Sitzung selbst, oder verlässt man sich auf die Middleware? → Kapitel 4
  2. Ausgeliefertes .git. Ist /.git/ über den Webserver abrufbar? → Kapitel 6
  3. Offene Speicher-Regeln. Sind Datenbank- oder Dateispeicher so eingestellt, dass jeder lesen oder schreiben kann? Das betrifft vor allem Dienste, auf die der Browser direkt zugreift. → Kapitel 4
  4. Preis aus dem Browser. Übernimmt der Server Preise oder Mengen, die der Browser schickt, statt sie selbst zu berechnen? → Kapitel 5
  5. KI mit zu viel Zugriff. Hat ein KI-Agent oder eine KI-Funktion mehr Rechte als nötig, etwa Zugang zur Produktion oder zu allen Mandanten? → Kapitel 1 und Kapitel 11
  6. Schwaches Session- oder JWT-Geheimnis. Ist das Geheimnis, mit dem Sitzungen oder Tokens signiert werden, lang, zufällig und nicht im Code? Ein JWT (JSON Web Token) ist ein signierter Datensatz, der einen Nutzer ausweist. → Kapitel 3
  7. Fehlende E-Mail-Bestätigung. Lassen sich Konten auf fremde Adressen anlegen? → Kapitel 3
  8. Login-Limits. Sind Fehlversuche begrenzt, und zwar je E-Mail, nicht für alle zusammen? → Kapitel 3
  9. Abfragen von Nutzer-URLs durch den Server (SSRF). Ruft der Server Adressen ab, die ein Nutzer eingibt (etwa Bild-Links)? Dann muss er interne Adressen sperren. SSRF (Server-Side Request Forgery) heißt: Ein Angreifer bringt den Server dazu, für ihn interne Dienste abzufragen.
  10. Reset-Link aus dem Host-Header. Wird der Link zum Passwort-Reset aus einer fest eingestellten Adresse gebaut? → Kapitel 3
  11. Source Maps. Werden in Produktion .map-Dateien ausgeliefert? → Kapitel 6
  12. Einbetten in fremde Seiten (Framing). Lässt sich die App in einem iframe einer fremden Seite anzeigen? → Kapitel 6
  13. Offene Weiterleitungen. Leitet eine Adresse auf beliebige fremde Ziele um? → Kapitel 6
  14. Konten-Erkennung über Antwortzeiten. Antwortet die App bei bekannten Konten messbar langsamer oder schneller als bei unbekannten? → Kapitel 3
  15. Verwaiste DNS-Einträge. Zeigen DNS-Einträge auf Dienste, die man nicht mehr nutzt? → Kapitel 2
  16. Veraltete Basis-Images. Wann wurden die Basis-Images der Container zuletzt erneuert? → Kapitel 7
  17. Analyse-Skripte im eingeloggten Bereich. Laufen Tracking- oder Chat-Skripte auch auf Seiten mit Kundendaten? → Kapitel 5
  18. Zähler ohne atomare Buchung. Werden Guthaben, Kontingente oder Lagerbestände so gebucht, dass zwei gleichzeitige Anfragen nicht beide durchkommen? Atomar heißt: Prüfen und Buchen passieren in einem einzigen, unteilbaren Schritt. Sonst lässt sich ein Guthaben durch viele gleichzeitige Anfragen mehrfach ausgeben.
  19. Kritische Framework-Lücken. Gibt es für das eingesetzte Framework eine bekannte kritische Lücke ohne eingespieltes Update? → Kapitel 8
  20. Geheimnisse im Code. Stehen Schlüssel, Passwörter oder Tokens im Code oder in der Versionsgeschichte? Ein Geheimnis, das einmal im Code stand, gilt als bekannt und muss ersetzt werden.

Wie man die Prüfung durchführt

  • Erst alle 20 Punkte prüfen und das Ergebnis festhalten, dann reparieren. So sieht man das Gesamtbild.
  • Jeder Fund wird ein Ticket mit Termin.
  • Nach jeder Reparatur den Punkt erneut prüfen.
  • Die Liste regelmäßig wiederholen, mindestens vor großen Releases.

So macht es ASEIO

ASEIO hat alle 20 Punkte durchlaufen. Funde wurden als Tickets umgesetzt und danach erneut geprüft. Restpunkte werden in einer Liste mit Termin verfolgt. Viele Punkte sind inzwischen fest im Prüflauf vor jedem Deploy oder in der monatlichen Wartung verankert, damit sie nicht wieder auftauchen.
