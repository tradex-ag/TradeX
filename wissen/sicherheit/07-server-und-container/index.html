7. Server und Container

Warum es wichtig ist

Wer einen eigenen Server betreibt, ist für alles verantwortlich, was darauf läuft. Ein offener Port, ein Container mit Root-Rechten oder ein veraltetes Image reichen, damit ein Angreifer von einer kleinen Lücke zur ganzen Maschine kommt. Gute Server-Sicherheit begrenzt, was ein Fehler anrichten kann.

Was man konkret tut

  • Firewall: Nur der Webserver ist von außen erreichbar. Eine Firewall lässt nur ausgewählte Verbindungen durch. Ein Port ist eine nummerierte Tür eines Servers, über die ein Dienst erreichbar ist. Von außen offen sind nur die Ports des Webservers. Die Datenbank und interne Dienste bleiben zu.
  • SSH nur mit Schlüssel. SSH ist der verschlüsselte Fernzugang zum Server. Mit einem SSH-Schlüssel statt Passwort kann niemand den Zugang durch Raten knacken. Die Anmeldung per Passwort wird abgeschaltet.
  • App-Container laufen ohne Root-Rechte. Root ist der Benutzer mit allen Rechten. Läuft ein Container als Root und wird übernommen, hat der Angreifer viel mehr Möglichkeiten. Das gilt auch für den Container, der Datenbank-Migrationen ausführt. Eine Migration ist ein Skript, das den Aufbau der Datenbank ändert.
  • Basis-Images per Digest festnageln und regelmäßig erneuern. Ein Basis-Image ist die Grundlage eines Containers, etwa ein schlankes Linux mit Node.js. Ein Digest ist ein eindeutiger Fingerabdruck einer genauen Image-Version. Festnageln heißt: Jeder Build nutzt genau dieselbe Version, niemand kann sie heimlich austauschen. Aber: Ein fester Digest bekommt keine Sicherheitsupdates. Deshalb muss man ihn regelmäßig bewusst auf eine neue Version heben.
  • Eine schriftliche Prüfliste für den Server, die nur liest. Sie fragt regelmäßig ab: offene Ports, Firewall-Regeln, automatische Updates, Container-Versionen, Stand der Sicherungen. „Nur lesen“ heißt: Die Prüfung ändert nichts, also kann sie auch nichts kaputt machen.
  • Grenzen für Logs und gleichzeitige Hintergrundaufgaben. Ohne Grenzen kann ein einzelner Fehler in einer Schleife die Festplatte mit Logs füllen oder so viele Aufgaben starten, dass der Server stehen bleibt. Logs werden in der Größe begrenzt und regelmäßig abgelöst, Hintergrundaufgaben laufen nur in fester Anzahl gleichzeitig.

So macht es ASEIO

Auf dem ASEIO-Server ist von außen nur der Webserver erreichbar, SSH geht nur mit Schlüssel. Alle App-Container laufen ohne Root-Rechte, auch der Migrations-Container. Die Basis-Images sind per Digest festgelegt und werden im Rahmen der monatlichen Wartung erneuert. Eine schriftliche Prüfliste fragt Ports, Firewall, automatische Updates, Container-Versionen und Sicherungen ab, ohne etwas zu ändern. Logs und gleichzeitige Hintergrundaufgaben haben feste Grenzen.

Woran man erkennt, dass es klappt

  • Ein Port-Scan von außen findet nur die Ports des Webservers.
  • Ein SSH-Login mit Passwort wird abgelehnt.
  • In jedem App-Container läuft der Prozess unter einem normalen Benutzer.
  • Das Datum der letzten Image-Erneuerung ist bekannt und nicht älter als der Wartungsrhythmus.
  • Die Prüfliste wird regelmäßig ausgeführt und das Ergebnis festgehalten.

Typische Fehler

  • Die Datenbank für einen Test von außen erreichbar machen und es vergessen.
  • SSH mit Passwort „nur übergangsweise“ erlauben.
  • Container standardmäßig als Root laufen lassen, weil es so am wenigsten Ärger macht.
  • Ein Image einmal festnageln und nie wieder anfassen.
  • Server-Prüfungen, die nebenbei Einstellungen ändern.
  • Logs ohne Größenbegrenzung.
